# Loop Engineering: Verifier, State und Stop-Bedingung als Mindestausstattung eines Agent-Loops

Der X-Artikel erklärt Loops als Ziel, auf das ein Agent ohne Prompt pro Schritt hinarbeitet, und stützt sich auf Karpathys `autoresearch` und eine Bilevel-Arbeit. Das Gerüst (Verifier, State, Stop-Bedingung, Eignungstest) ist fachlich solide. Die Zahlen zu Karpathy, Tobi Lütke und dem „5x“ sind unbelegte Weitergaben ohne Link zur Quelle.

## Drei Pflichtteile und ein Eignungstest

- **Verifier:** ein Test, eine Metrik oder ein Build, der Arbeit ohne Mensch ablehnen kann. Ohne ihn „bewertet der Agent seine eigenen Hausaufgaben“.
- **State:** eine kleine Datei mit Erledigtem, Gescheitertem und nächstem Schritt, damit der nächste Lauf nicht bei null beginnt.
- **Stop-Bedingung:** Ziel erreicht oder hartes Limit („nach N Versuchen stoppen und berichten“).

Ein Loop lohnt sich nach der Quelle nur, wenn alle vier Punkte zutreffen: Die Aufgabe wiederholt sich mindestens wöchentlich, die Verifikation ist automatisiert, das Token-Budget verträgt Verschwendung, und der Agent hat echte Tools (Logs, Reproduktionsumgebung, Code ausführen). Auf einem 20-Dollar-Plan sei ein schwerer Loop riskant.

## Karpathy-Loop und Bausteine

`autoresearch` besteht laut Quelle aus drei Dateien: `train.py` (einzige Datei, die der Agent ändern darf), `prepare.py` (Evaluator, für den Agenten gesperrt, sonst würde er den Test erleichtern) und `program.md` (Anweisungen). Der Zyklus: Code lesen, Änderung vorschlagen, fünf Minuten trainieren, bei Verbesserung committen, sonst Rollback. Das Diagramm nennt rund 12 Experimente pro Stunde, etwa 100 über Nacht. Genannte Ergebnisse: 700 Experimente in zwei Tagen, 20 gefundene Verbesserungen, bei Tobi Lütke 19 % Qualitätsgewinn mit halb so großem Modell. Der Ausgangsstand war von Hand getunt.

Fünf Bausteine nennt der Autor für Claude Code und Codex: Automation (`/loop`, `/goal`, Codex Automations), Skill als Projektgedächtnis, Subagents zur Trennung von Ersteller und Prüfer (schneller, billiger Writer; langsamer, strenger Reviewer), Connectors (PR öffnen, Ticket updaten) und Verifier.

## Bilevel Autoresearch

Ein Paper (März 2026) setzt über den inneren Loop einen äußeren, der Code und Traces des inneren liest, Stagnation erkennt und neuen Python-Code zur Änderung der Suchstrategie injiziert. Angegeben: -0,045 gegenüber -0,009 `val_bpb` auf Karpathys GPT-Pretraining-Benchmark („5x“), beide Ebenen mit demselben LLM. Der Gewinn komme aus der Architektur. Der äußere Loop breche die Priors des Modells, auf die der innere immer wieder zurückfällt.

## Grenzen laut Quelle

Comprehension Debt (Lücke zwischen Repo-Inhalt und eigenem Verständnis wächst mit der Loop-Geschwindigkeit) und Cognitive Surrender (Ergebnisse ungeprüft akzeptieren).

## Einordnung

Belastbar ist die Struktur: Verifier, gesperrter Evaluator und Stop-Limit entsprechen gängiger Harness-Praxis. Karpathy-Zahlen, Lütke-Anekdote und das „5x“ sind selbstberichtet bzw. weitergereicht, der Vergleich beruht auf einem einzelnen Benchmark mit sehr kleinem Absolutwert. Kosten (Token, Rate Limits) benennt die Quelle nur qualitativ, ohne Zahlen. Die Aufgabe „Metrik steigt“ ist beim Modelltraining klar definiert, bei Produktcode ist der Verifier der schwierige Teil. Wenig Neues gegenüber dem Bestand, aber die Vier-Punkte-Prüfung ist eine brauchbare Entscheidungshilfe.
