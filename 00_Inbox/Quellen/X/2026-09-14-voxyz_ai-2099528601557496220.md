## Post-Text

Codex tip: Have Astra check what it builds, not just the code.

You ask it to “check your work when you’re done.” It runs the tests and tells you everything is ready. But if it never opens the page, you’re still the first person to try using the feature.

You find a problem, send back a screenshot, and it makes another fix. You haven’t handed off that final check, so you’re still spending time on the back-and-forth.

Make your acceptance criteria specific enough to follow. Take a profile editing page:

UI: Do the layout, typography, and spacing work on desktop and mobile? Are any buttons obscured? If you have a design reference, compare it with the actual page.

UX: Is it easy to fill in the form, save, and cancel? Can users tell what’s happening while the page loads, when an input is invalid, and after saving?

Functionality: After saving and refreshing, is the updated information still there? Has the change affected any existing behavior?

I think the Codex desktop app’s built-in browser is the best and smoothest option right now. The prompt below uses @Browser; this built-in browser isn’t included in the CLI or IDE extension.

Add this to your next request 👇

“What we’re building: [the page or feature, and the problem it should solve]
What to verify: [the actions that should work, expected results, and any design or usability requirements that matter to you]

If I leave either field blank, fill it in from the current task and existing requirements. Ask me about anything you’re unsure of. Use @Browser to open the running page, interact with it, and check it against these requirements. Cover the relevant desktop and mobile layouts and page states. If there’s a design reference, compare it with the rendered page. Include key screenshots and check results, and clearly state anything you didn’t verify.”

For web pages, check the actual page. For APIs, check the actual response. For scripts, check the actual output.
