Hello, folks. Having a good conference so far? Okay, good. So I'm here to talk about fixing the PR bottleneck. And this is kind of a grand title for trying to fix the thing that most organizations struggle with, I think, and have kind of historically struggled with, before AI. We have always had huge numbers of PRs just laying around that no one's bothered to review, and this has now increased massively because of the new strains on us from AI imposing all these weird constraints. To do this, I'm going to use the rubric of my skills, which you've maybe heard about, maybe used. I have a couple of new skills to announce that are hopefully going to improve the way that you do PRs — improve the speed at which you can review them and do them.

Speed. Now we're being pushed to do more with less, essentially — more PRs, more work, more stuff. And this is kind of the central promise of AI: that we're going to be able to use these agents to scale ourselves up to do more work. This has resulted in the "software factory" — probably the biggest buzzword of the day, everyone's talking about it. I think of a software factory as primarily something where, instead of the human initiating all of this work, some of that initiation is going to be done by agents.

All of this is not humans triggering it — it's deterministic code triggering it. And so these accelerate your software factory: they push more code through it. But then you need brakes. If you just have permanent acceleration pushing stuff through your factory, you're going to end up with a slop cannon — you're just going to end up with a ton of slop, crappy PRs that you're not going to be able to touch, or review, or even look at. So you need brakes: mechanisms that slow down, that increase quality, that make sure your codebase doesn't turn into a software-entropy nightmare, because code is the environment your agent operates in, and if you have bad code in your codebase, that is going to beget more bad code.

So I'm going to talk about three brakes in this talk, and how we can use them to counterintuitively go faster. The first is automated checks — the deterministic checks in your repo that we've had for decades, since the '50s: linting, tests, type checking, code-quality metrics. All of these things work together, and they all work the same way every time. Layered on top of that is automated review: agents who look at your code and catch the things the tests didn't catch, or look at the structure of the codebase in general. And then, on top of that, the third and final layer is human review — people looking at the PR. These three layers form a kind of cake that we end up with when we get to human review. More speed, of course, means more PRs, so the goal here is to make human review faster by leaning on those first two phases.

And we've got to stop the slop. That's the first principle here: if you raise the quality of the code that you're shipping, you're going to end up doing less human review, because it's just going to be better work, and you're going to end up needing to make fewer interventions.

So — automated checks. Automated checks are cheap. That's the cool thing about them: they don't cost tokens like automated review does, they don't cost human effort, they just cost CPU cycles. For instance, you run your tests on every code change — maybe those tests do incur some tokens, because let's say an agent creates a bug and the tests catch it, then you need to spend some tokens to go and fix it, but those are tokens pretty well spent, in my opinion. So checks are cheap, which means you can layer on loads and loads of them on your repos — you're probably not using enough of them, or not being creative enough with your use.

But checks can lie. Does a green CI mean the code is ready to merge? No, it does not. So we've always needed, on top of these checks, some extra layer to figure out if there's anything catastrophically wrong with the code before we ship it. All of the other phases — human review and automated review — are lie detectors: they're for finding lies in the automated checks. I want to show you some of these lies first, because it helps, when we're thinking about code and automated checks, to see how bad things can get.

The first is tautological tests — a test that just reasserts the implementation. Opus 5 got addicted to these. I don't quite understand why it would — for instance, "X post character limit equals 280." Can anyone guess the test that was written to test this behavior? You've probably seen this a thousand times; this is real code from agents, or from stuff I found my agents doing. It said: expect X post character limit to be 280. So the implementation looked like that, and the test essentially reasserted the implementation — that's a tautological test. Tautological tests are bad because they're extremely structure-sensitive, very sensitive to the actual internal workings of the system. It means I can't change that constant without a test failing, I can't rename that constant without a test failing — the test is too tied into the structure of my system.

I found another one that's even more egregious, I'd say — an incredible test. What it's doing is essentially testing whether two things in the UI appear in the right order: it's checking that the video section comes after the content plan on the pitch-detail page. What it does is it doesn't render anything to a screen — it just reads the actual module file into its own memory, finds "content plan," finds "videos," and then expects "videos" to come after it in the source material — which is crazy if you think about it, because I can just change the way the source material looks and this test will fail. It's too sensitive to the structure of my codebase. That's another way automated checks can lie.

There are also tests that literally cannot fail — and this will feel familiar if you've abused mocking in the past. For instance, here we have a "use audio boost" function, and its internals use the Audio Context API in the DOM. Don't worry if you don't know any of this, but what we're doing here is just stubbing it out with some fake methods. It turns out the Audio Context API has some complicated error modes, and it will fail if you use it under strange conditions — so just doing this means our tests can't fail using those modes, and we're going to hit strange errors in production that our tests can't catch.

So the question is: if you can cheat on automated checks — even in good-faith ways, the AI isn't trying to write bad tests here, it's just taking our instructions and writing tests that are too tied into the structure instead of actually executing code — how do we make automated checks harder to cheat? If we can do that, we increase the quality of those checks, which raises our quality bar.

The first thing I really like here is codebase design — you can actually design your way out of these bad checks. What does good codebase design look like? I've talked about this before in previous AI Engineer talks: deep modules. These are modules that hide complex behavior behind simple interfaces — this is a John Ousterhout idea, from "A Philosophy of Software Design." If we look at two modules: A has a large implementation hiding behind a tiny interface at the top; B is a large interface with lots of functions you can call, and those functions individually don't do very much. If you have a deep module like A, you're going to have fewer structure-sensitive tests, because you're hiding more of the implementation behind that interface — if it's just testing at that interface, you get better tests. So your job is to force the agent to use that little interface instead of reaching into the implementation to test weird implementation details.

I've got a skill for this. You can take the weirdest vibe-coded, crappiest codebase you've ever set your eyes on, run this skill on it, and it will make it better. What it does is give you opportunities for deepening modules. It essentially gives you an HTML document with all of the different opportunities it sees: you get a before and an after, where you're reducing duplication and creating a nice, deep, testable module that you can go and implement. Attached to this, there's also a little vocabulary I've put together for describing modules, because if you ever try to read up about how to structure a codebase, you'll find twenty different approaches, and they'll all be called "DDD." What you need is a consistent language your team can use to talk about this stuff. So I have a codebase-design skill that defines what "locality" is, what "leverage" is, what a "seam" is — I was using seams before they were cool. Locality is roughly how well-located together all the code is: can a small change in one module ripple out? Leverage is what you get from a deep module, because the caller gets a lot of value from calling a simple function. Both are very good in codebases, and it turns out they're good for agents too.

But I'm describing all these high-level coding standards — how do we actually make sure the agent follows them? How do you make sure the agent creates deep modules and good tests, and doesn't write these tautological or structure-sensitive ones? I think most people get this wrong. My first piece of advice: don't put coding standards in your implement agent. Let me explain. Imagine the implement agent's context window contains everything it needs to do in a single pass: it needs to explore, to find the code it's going to change; then it needs to actually change it, make the updates to the files; and then it needs some budget for actually debugging — running automated checks, verifying that it works. That's already quite a lot of work, and if you try to impose your coding standards on top of that too, it's going to perform worse. So the implement step is overloaded — that's the mental model I want you to have.

Can we find a way to impose coding standards without overloading it? That's my code-review skill. It receives a diff, reads a file inside the repository called something like `coding-standards.md`, which you write and customize, and checks whether the code follows those standards. The reviewer agent runs in its own sub-agent, with its own context window and its own budget. It needs to do some exploration too — sure, it receives the diff, so it knows exactly where the code is, but it should do a bit of exploration to get wider context — but it doesn't need to do any implementation or debugging. So while implementation is overloaded, review is actually underloaded — it doesn't have that many jobs to do. That means you can pile a bunch of coding standards into it, and it will do a much better job than if you tried to do it in implement.

So I think of this — and it's a little uncomfortable, because we all want to just get good code out the first time — as a two-part process for writing good code: implement makes it work, and code review makes it good, by imposing your coding standards. For the TDD crowd among us, this is essentially a red-green-refactor approach: one context window does red-green, and another context window refactors. That's at least how it works in my head, and it's been very successful for me. This means when you have coding standards, you don't put them in global scope — you don't put them in `AGENTS.md`, because then they get drowned out by everything else the implement step reads (it may read them, it may not). You put them in `coding-standards.md`, so only the code-review agent reads them.

I've got another idea here — I've been talking to a lot of people today about how automated review can help fix the PR bottleneck, and a lot of people say "oh, we just use a third-party service, we use Cursor's Bugbot, we use CodeRabbit, or something like that." I've really tried, in the past, to make a generic code-review skill that finds all the bugs and does security review and that kind of thing — it turns out that's really, really hard, because you either make it too general, and it just gives you false positives that aren't relevant to your use case, or you make it too specific — you say "okay, find all the TypeScript stuff," and then the Rust people can't use it. So I'd say: don't outsource automated review, build your own. Build up your own coding standards over time, and share them across your team. If you have some docs sitting around that no one reads, this is the place to put them.

Also, when you have this automated reviewer, a really natural inclination is to say "my code-review agent reads the code and then comments on the PR." But what your code-review agent is doing in that case is creating more work for the human reviewer — they now have to read all these verbose comments and figure out whether to implement this or that. The reviewer should commit — it should make fixes, actually change the things it finds — so that when the human comes around, they're reviewing a nice, finished artifact. If it has any genuine questions, of course it can comment, but the default should be commits. Stop trying to one-shot good code with just the implementer agent — force it to be amazing with a second pass. It takes a bit of rethinking, but once you get it, it's fabulous.

So, with all of that: we've run our automated checks, we've run our automated review to make sure the checks aren't lying — how do we then maximize the PR's quality for human review, how do we make it work as well as it can? We need a human-friendly PR. This is a new skill coming into the repo, currently in progress, that I'll be releasing soon: the PR skill. I've been mulling this one over for a long time — I hadn't quite figured out what the state of the art was, and I realized the best way to make a PR skill is just to steal all the best ideas everyone's got.

What does a good PR body look like? The first principle: some reviews are more important than others — not every review is essential. Once you understand this, you realize you can focus your energy on the really important reviews. How do we categorize that? You think about the PR using the AWS terminology: is it a one-way door, or a two-way door? Most PRs you have will be two-way doors — you can merge the PR and always pull it back later. That's the glorious benefit of being a software engineer instead of a civil engineer: for a civil engineer it's mostly a one-way door — get something wrong, and that bridge is going down. A two-way door means you can easily revert the change. That might be a bit more nuanced than you'd expect, though — a very simple change might accidentally blast an email out to 60,000 people, in which case that's a one-way door, and you want to review it very, very carefully. Anything that involves expensive migrations or data loss is a one-way door — review the hell out of that PR. Tied to that, we need to understand the blast radius of the PR: what can go wrong, and if it does, how bad is it? I end up with a little summary at the bottom of all my PRs called "merge danger": I can see this one's a two-way door, its blast radius is localized, so I don't need to pay much attention — I'll just review it a little. That's really important.

Next, we need to understand what the PR is even doing — I've tried lots of different ways of figuring this out, and the best thing I've come up with is using pseudocode. Big thanks here to the "show-me" skill from the HumanLayer skills repo by Dex Horthy — a phenomenal skill that dispenses with most of the text and shows things to you in images and diagrams instead. That makes it a lot easier to grasp what's actually changing and why. You get the standard set of Mermaid diagrams and UML — sequence diagrams for "this is the sequence of things that happened" — but you also get lovely, simple ones: for instance, we can look at one and see we're working in a CLI, a new command's been added, and there are two new flags at the top. Just little summaries like that make a massive difference — it's hard to overstate. You're trying to make understanding the "why" as fast as possible.

A third principle: something you should think about whenever you do human review, because our processes are now so streamlined, and we're all collaborating around the same skill files, the same steering files — we're all building an environment for our agents to operate in together — you should think of the process that produces your code as just as important as the code itself. In other words, when you do a human review, you're not just reviewing the code, you're reviewing the system that creates it. The theory here is that you never want to write the same comment twice — you never want to catch the agent doing the same thing across two PRs. So what's the mechanism that makes your human review matter? This is a new skill: retro, for "retrospective." You take a session you've done — it can be a single agent session, or a PR plus the session, or you can just point it at all the PRs and reviews you've done over the last week and say "let's do a retrospective on them," and it will suggest automated checks and coding-standard updates to make the next one better.

This is the compounding effect: by doing human review, you're making the quality of the next human review higher, and saving yourself work next time. Retro is a really smart skill — obviously it suggests automated checks and updates to `coding-standards.md`, but it does other smart things too. It looks at navigation pointers: how easily did the agent find its information, and can we add a pointer inside `AGENTS.md` to help it out next time? It looks at tool economy: are there different tools being used in the session that could be made more token-efficient? It's amazing how many things this catches — those are often really hard to debug from the outside. It also looks at bloat: are there bloated steering files, bloated skills, contributing to bad results — can we make them more organized?

So that's the goal: make human review faster by layering up automated checks and automated review, and make human review itself as painless, simple, and optional as it needs to be. You really don't need to review every single two-way door; every single one-way door, you do.

And so — these are my skills, at aihero.dev/skills. I'm going to be shipping version 1.3 this week. It's been glorious hanging out with you, it's been a really nice conference. I'll be outside in the lobby if anyone wants to chat. Thank you so much for having me. Thank you, Paris.
